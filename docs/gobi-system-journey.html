Section 01/System Overview
Section 01 · System Overview

One shipment record that every party works from

Gobi is an operational coordination workspace for freight. A shipper, a carrier, a clearing agent and a driver all read and update the same shipment: one lifecycle, one structured timeline, one document checklist, checks before dispatch, a payments ledger and an audit trail. It replaces the WhatsApp messages, phone calls and spreadsheets that coordinate freight today.

~10 minExpress API · Next.js web app · PostgreSQLDesign principle: manual first, integration ready
The problem

What Gobi fixes

Each card is a coordination failure the code is built to prevent.

Status lives in chat threads

Pickups, border crossings and delays arrive as messages nobody can search. Gobi records each one as a typed timeline event with who, when, where and notes.

Missing papers are found at the border

Gobi creates the required-documents checklist when the quote is approved, and its Document Gate blocks dispatch until every mandatory document is in.

Unfit trucks and drivers get dispatched

The Compliance Gate checks driver approval, licence and vehicle expiry dates and weights before a vehicle and driver can be assigned.

No proof of who decided what

Each change writes an immutable audit row. A gate override must include a written reason, and the audit row keeps the exact failures that were overridden.

Section 02 · People & Organizations

Accounts, organizations and roles

Access in Gobi has two layers. A platform account is either a normal user or a platform admin. Separately, a user holds an organization membership with a role in each company they belong to. Shipment access comes from the second layer: how your organization relates to that particular shipment.

~12 min3 organization types4 organization roles + platform admin

Platform account

Created only after the person proves their email with a 6-digit code (15 minutes, 5 tries, 30-second resend cooldown), or at once when they register from an invitation link for the same email. users.type is user or admin. A new account belongs to no organization.

Sign-up grants no operational role. Tested

Organization (company)

Every organization has one companyType: distribution (shipper), transport (carrier) or clearing_agent. Any signed-in user can create one of any type and becomes its owner. There is no approval or verification step for organizations.

Membership role

One role per person per organization: owner, coordinator, member or driver (transport only). Memberships are loaded from the database on every request, not baked into the login token, so a role change or removal takes effect on the very next call.

Two different things

Hidden in the interface vs. refused by the API

The demo audience sees the interface, but permissions live in the API. Keep the two apart when you explain them.

Hidden in the web app

  • The sidebar is built from your platform type, the acting organization's type and your role (components/layout/nav.ts). Its own comment says: "This only decides which links are shown; the API enforces every permission independently."
  • Most shipment buttons read access.can, a per-action yes/no that the API computes from the same policy table and sends with GET /shipments/:id. A few panels use their own role-and-status checks that match those rules.
  • /dashboard/admin/** is redirected by Next.js middleware for anyone who isn't a platform admin.
  • Hiding a button is a convenience. It's not security.

Authorized or refused by the API

  • Every shipment route runs authorizeShipment(action). It loads the shipment (or the document, payment or exception it belongs to), works out your relationship to it and applies the policy before any work happens.
  • Wrong party → 403 with the policy's denied message. Right party, wrong status → 400 with its wrongStage message.
  • On upload routes the check runs before the file is read, so a refused caller's file is discarded unread. Tested
  • Calling the API directly (curl, Swagger) gets exactly the same answers as the web app does.
Section 05 · Documents Explained

The document checklist and what it proves

Gobi's catalogue has 10 shipment document types (config/shipmentDocuments.js). Approving the quote creates the checklist: 4 rows for a domestic shipment, 10 for a cross-border one. Read the three columns below first. Gobi stores a file, people review it, and Gobi never checks whether it's genuine.

~12 minPDF · JPG · PNG, max 10 MBPrivate storage, 5-minute view links

What Gobi stores

  • The uploaded file, after checking its real type from the leading bytes (a renamed .exe is refused)
  • Stored as a private Cloudinary asset. Responses never include a raw link
  • Viewing goes through GET /shipments/documents/:docId/file, which re-checks that you're a shipment party and returns a link that expires after 5 minutes
  • File name, type, size, uploader and time

What "verified" means

  • A carrier owner/coordinator (or a platform admin) looked at the file and clicked Verify. Gobi records who and when
  • It's a human review. Gobi doesn't read the content, check signatures or stamps, or contact the issuing authority
  • Verification doesn't open the gate. An uploaded, unverified document already counts. Only rejection changes the gate

What Gobi just records

  • That someone supplied a file for a checklist row (status uploaded)
  • An optional expiry date, which only the API accepts (the upload form has no date field)
  • Seeded demo documents have a file name only, no stored file, and show "no file stored"
  • Vehicle insurance, inspection and Yellow Card are dates on the vehicle, not uploaded files. The driver licence is a typed number and date, with no image

Section 07 · Fleet & Driver Compliance

Vehicles, drivers and the Compliance Gate

A carrier registers vehicles with expiry dates. Drivers join by invitation and submit their licence details, which a platform admin approves. All of it comes together at one point: the Compliance Gate that runs when a vehicle and driver are assigned to a shipment.

~12 minSource: complianceGate.service.js, vehicles + driver + admin controllers
Three separate things

Membership, approval and shipment access are independent

Each is stored and granted separately. A driver needs the first two before they can be assigned without an override, and the third follows from the assignment.

1

Carrier membership

An organization_members row with role driver in a transport organization, created only when the driver accepts an invitation.

  • Granted by: the carrier's owner/coordinator (invite) + the driver (accept)
  • Allows: being picked as that carrier's driver
  • On its own: shows no shipments

Ends when the owner removes the member.

2

Driver profile approval

One driver_profiles row per person, for the whole platform: licence number, expiry date and status pending / approved / rejected.

  • Granted by: a platform admin
  • Allows: passing the driver part of the Compliance Gate
  • Follows the person to any carrier they join

Not tied to any organization.

3

Shipment access

Exists only while shipment.assignedDriverId is this user and they're still an active driver of that shipment's carrier.

  • Granted by: a carrier owner/coordinator's assignment
  • Allows: view, milestones, pickup/arrival, POD, uploads, exceptions
  • Never includes quotes or payments

Lost immediately if the membership ends. Tested

Driver path

From invitation to first assignment

Fleet

Vehicle registration and the seeded fleet

Only owners and coordinators of a transport organization can register, edit or delete vehicles. Plate numbers are unique across the platform. Every member of the carrier can list its fleet through the API. The expiry badges below use today's date in your browser, the same way the gate compares dates.

Tested

Closed shipments then lose the link to the vehicle (the database sets it to null), but their timeline text still names the plate.
Code
Who sees the fleet. Any active member of the acting transport organization can list it, drivers included. The web app hides the Fleet page from drivers and hides the edit controls from members. Assignment only offers the shipment carrier's own vehicles. Another carrier's vehicle is refused with the same message as a vehicle that doesn't exist.
The gate

Compliance Gate checks

Run by GET /shipments/:id/assignment-preview (live, as choices change) and again by POST /shipments/:id/assign. Dates count as expired when they're before the start of today. Warnings never block.

Override

Exactly what an override can and can't do

It can

  • Assign despite any Document Gate or Compliance Gate failure, including a driver with no approved profile, an expired licence, an overweight load or a load above 56 t Tested
  • Override the two gates separately (overrideDocumentGate, overrideComplianceGate). The web app sets whichever one is failing
  • Leave permanent evidence: a gate_overridden timeline event that every party sees, plus audit metadata with the reason, the missing documents and the compliance failures at dispatch time Tested

It can't

  • Run without a written reason (5–500 characters) → 400 overrideReason is required when overriding a gate
  • Be used by anyone except the carrier's owner/coordinator, or outside awaiting_documents / documents_complete
  • Bring in a driver who isn't an accepted, active driver of this carrier, or a vehicle from another fleet. Those are hard refusals that run before the gates
  • Fix anything: the driver stays unapproved and the vehicle dates stay expired
  • Be undone. There's no endpoint to re-assign the vehicle or driver
Disclosure: licence review isn't licence verification. A driver types a licence number and an optional expiry date. No licence image is uploaded, no registry is checked and no identity documents are compared. A platform admin approves or rejects what was typed (there's no field for a rejection reason). An approval means "an administrator reviewed the submitted details". It doesn't independently prove the person's identity or that the licence is genuine.
Renewal gap. Once a profile is approved, the driver can't resubmit it (409 "Your driver profile is already approved."), so an expired licence can't be renewed from the web app. Through the API, an admin can set the profile to rejected (PATCH /admin/drivers/:id), the driver resubmits, and the admin approves again. The admin screen shows review buttons only for pending profiles. Code
Section 08 · Notifications & Audit Trail

Email, the shipment timeline and the audit log

Gobi keeps three different records, and they're easy to mix up in a demo. Emails tell people to act. The timeline is the operational diary that every shipment party sees. The audit log is the platform admin's record of who changed what.

~10 minNo in-app notification centre · no push

Email (Brevo)

Sent in the background for hand-offs and account events. It never delays or fails the action, never goes to the person who acted, and skips inactive users and duplicates. Shipment emails go to owners and coordinators of the relevant organizations, plus the assigned driver for assignment and cancellation.

Shipment timeline

shipment_events: 17 system event types written by platform actions and 14 manual types recorded by people. Each records its type, actor, time, optional place text, notes, metadata and source (manual or system). Every shipment party can read it. The driver sees it with amounts removed.

Audit log

activity_logs: one row per change, with actor, role, acting organization, action, entity, description, metadata, IP address and time. Rows are never updated. Only platform admins can read it (GET /admin/activity-logs, latest 100 by default, at most 500).

Email

Which events send an email, and to whom

From services/notifications.service.js. Development and demos can send every email to one inbox with EMAIL_REDIRECT_TO. The intended recipient is then shown in the subject.

No email for: shipment created or submitted, document uploaded or verified, gate overridden, payment recorded or settled, exception resolved, any manual milestone (including pickup and arrival), role changes, removals, invitation accepted or revoked. Someone who registers from an invitation link doesn't get a welcome email either.
Timeline

System events written automatically

Manual events (pickup, checkpoints, border, customs, warehouse, arrival, notes) are covered in the journey. Only picked_up and arrived_destination change the status. Timeline entries can't be edited or deleted through the API.

Audit

What the audit log captures, and what it doesn't

Actions written to activity_logs

Not audited

  • Sign-ins, failed sign-ins, token refresh
  • Profile edits and password changes (the constants UPDATE_USER_PROFILE and CHANGE_PASSWORD exist but nothing writes them)
  • Viewing documents, files, payment proofs or shipments
  • Assignment previews, verification-code requests and resends
Best effort. If writing an audit row fails, the error is logged and the action still succeeds. So "audit coverage" means "an audit write is attempted for each change", not a guarantee. Code
Role column caveat. actorRole and organizationId are taken from the caller's acting organization (the switcher header), or platform_admin. For a person in several organizations, that may not be the organization that's a party to the shipment. Code
Absent

Not implemented

Notification centre

There's no inbox, bell or unread count in the app.

Live updates

No WebSocket, server-sent events or polling. React Query doesn't refetch on window focus, so other people's changes appear when you reload or move between pages.

SMS / WhatsApp / push

Email is the only outbound channel.

Preferences

There's no per-user opt-out or digest. EMAIL_ENABLED=false switches email off for the whole server.
